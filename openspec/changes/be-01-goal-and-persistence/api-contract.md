# Interface and data contract: Goal and local database baseline

- **OpenSpec Change ID:** `be-01-goal-and-persistence`
- **Proposing team:** be (backend team)
- **Related proposal:** `proposal.md`
- **Related specifications:** `specs/fun-01-portfolio-goals/spec.md`, `specs/tech-02-local-database-baseline/spec.md`
- **Related design:** `design.md`

## 1. Purpose and scope

Establishes the first HTTP surface and the first stored entities: goals owned by Siddhi,
their revisions, and the schema version of the local SQLite database. Nothing in this
contract reads a source system. Project association, analysis, planning and external
analysis are excluded and have no placeholder fields here.

## 2. Conventions

- Transport: HTTP/1.1 over the loopback interface only; JSON bodies, UTF-8.
- Timestamps: ISO-8601 UTC with an explicit `Z` suffix (`2026-10-29T12:00:00Z`). Dates
  without a time use `YYYY-MM-DD` and are interpreted as UTC dates.
- Identifiers: UUIDv4 strings generated by the server. Clients never choose them.
- Media type: `application/json`.
- Every response carries `X-Correlation-Id`; error bodies repeat it.
- Unknown request fields are rejected as validation errors, not ignored.

## 3. Interface surface

### 3.1 `POST /goals` — create a goal

Request:

```json
{
  "title": "Publish the Siddhi architecture note",
  "outcome_type": "publication",
  "description": null,
  "rationale": null,
  "priority": null,
  "target_date": null,
  "success_criteria": null,
  "constraints": null,
  "assumptions": null,
  "risks": null
}
```

Required: `title` (1–200 characters, not blank after trimming), `outcome_type` (one of
`software`, `publication`, `research`, `internal_investment`, `other`). Every other
field is optional and defaults to `null`; a `null` field means *not recorded*.

Response `201`:

```json
{
  "id": "6f1c0a1e-3d5e-4a2b-9d4f-0c1b2a3d4e5f",
  "title": "Publish the Siddhi architecture note",
  "outcome_type": "publication",
  "status": "active",
  "description": null,
  "rationale": null,
  "priority": null,
  "target_date": null,
  "success_criteria": null,
  "constraints": null,
  "assumptions": null,
  "risks": null,
  "unknown_fields": ["description", "rationale", "priority", "target_date", "success_criteria", "constraints", "assumptions", "risks"],
  "revision": 0,
  "created_at": "2026-10-29T12:00:00Z",
  "updated_at": "2026-10-29T12:00:00Z",
  "archived_at": null
}
```

`unknown_fields` lists every field currently `null`. It is derived, never stored
separately, so it cannot disagree with the field values.

### 3.2 `GET /goals` — list goals

Query parameters: `status` (`active` | `archived` | `all`, default `active`),
`limit` (1–100, default 25), `cursor` (opaque, from a previous response).

Response `200`:

```json
{ "items": [ /* goal objects */ ], "next_cursor": "eyJvIjoyNX0", "has_more": true }
```

Ordering is `created_at` descending, then `id` ascending as a stable tie-break. The
cursor is opaque base64 of server state; clients must not construct or interpret it.
An invalid cursor is a `validation` error.

### 3.3 `GET /goals/{goal_id}` — retrieve one goal

Response `200` with the goal object. Unknown identifier → `404` `not_found`.
Archived goals remain retrievable.

### 3.4 `PATCH /goals/{goal_id}` — revise a goal

Request: any subset of `title`, `outcome_type`, `description`, `rationale`, `priority`,
`target_date`, `success_criteria`, `constraints`, `assumptions`, `risks`, plus:

- `revision_reason` (optional string, ≤ 500 characters) — stored with the revision.
- `expected_revision` (optional integer) — optimistic concurrency guard.

An explicit `null` clears a field back to unknown and is recorded as a change. An
absent field is untouched. `status`, `id`, `revision`, `created_at`, `updated_at`
and `archived_at` are server-owned and rejected if supplied.

`priority` accepts `low`, `normal`, `high`, `critical` or `null`. There is no numeric
priority score.

Response `200` with the updated goal (`revision` incremented by 1).

Errors: `404 not_found`; `409 conflict` when `expected_revision` is not the current
revision (body includes `current_revision`); `422 validation` for any rejected field.
No goal row or revision row changes on any error.

### 3.5 `POST /goals/{goal_id}/archive` — archive a goal

No request body required. Response `200` with the goal, `status: "archived"`,
`archived_at` set. Idempotent: archiving an archived goal returns `200` and creates no
new revision. Does not delete rows.

### 3.6 `GET /goals/{goal_id}/revisions` — revision history

Same pagination parameters as `GET /goals`, ordered by `revision_number` descending.

Response `200`:

```json
{
  "items": [
    {
      "revision_number": 2,
      "changed_at": "2026-10-29T13:10:00Z",
      "actor": "owner",
      "reason": "Publication date agreed",
      "changed_fields": ["target_date"],
      "prior_state": { "target_date": null, "priority": "high" }
    }
  ],
  "next_cursor": null,
  "has_more": false
}
```

`prior_state` contains only the changed fields' previous values. Revisions are
append-only; there is no update or delete operation for them.

### 3.7 `GET /health` — diagnostics

Response `200` when the service is usable, `503` when it is not:

```json
{
  "status": "ok",
  "schema_version": 1,
  "checks": {
    "service": { "status": "ok" },
    "database": { "status": "ok", "schema_version": 1 },
    "integrations": { "status": "not_configured", "detail": "no source adapters in this change" }
  }
}
```

`status` is `ok` only when service and database are `ok`. Integration readiness never
decides service usability. No path, credential, connection string or stored content
appears in this payload or in any error message.

## 4. Error model

```json
{
  "error": {
    "category": "validation",
    "code": "invalid_field",
    "message": "outcome_type must be one of software, publication, research, internal_investment, other",
    "field": "outcome_type",
    "correlation_id": "8a2f...",
    "details": []
  }
}
```

| Category | HTTP | Meaning |
|---|---|---|
| `validation` | 422 | Input rejected before any state change |
| `not_found` | 404 | The addressed goal does not exist |
| `conflict` | 409 | `expected_revision` does not match current state |
| `unsupported` | 400 | A requested operation or media form is not supported by this slice |
| `unavailable` | 503 | A dependency needed to answer is not usable (database) |
| `internal` | 500 | Unexpected failure; correlation id only, no internal detail |

`category` is the stable field clients branch on. `code` is a finer, additive
identifier; new values may appear in a category without a breaking change.

## 5. Data model (schema version 1)

```sql
CREATE TABLE schema_version (
    version     INTEGER PRIMARY KEY,
    applied_at  TEXT    NOT NULL
);

CREATE TABLE goals (
    id              TEXT    PRIMARY KEY,
    title           TEXT    NOT NULL CHECK (length(trim(title)) BETWEEN 1 AND 200),
    outcome_type    TEXT    NOT NULL CHECK (outcome_type IN
                        ('software','publication','research','internal_investment','other')),
    status          TEXT    NOT NULL CHECK (status IN ('active','archived')),
    description     TEXT,
    rationale       TEXT,
    priority        TEXT CHECK (priority IS NULL OR priority IN ('low','normal','high','critical')),
    target_date     TEXT,
    success_criteria TEXT,
    constraints     TEXT,
    assumptions     TEXT,
    risks           TEXT,
    revision        INTEGER NOT NULL DEFAULT 0 CHECK (revision >= 0),
    created_at      TEXT    NOT NULL,
    updated_at      TEXT    NOT NULL,
    archived_at     TEXT
);

CREATE TABLE goal_revisions (
    goal_id          TEXT    NOT NULL REFERENCES goals(id),
    revision_number  INTEGER NOT NULL,
    changed_at       TEXT    NOT NULL,
    actor            TEXT    NOT NULL,
    reason           TEXT,
    changed_fields   TEXT    NOT NULL,
    prior_state      TEXT    NOT NULL,
    PRIMARY KEY (goal_id, revision_number)
);
```

Invariants enforced in the write transaction, not by triggers:

- A goal write and its revision insert commit together or not at all.
- `goals.revision` equals that goal's highest `revision_number` (0 when none).
- Archival sets `status` and `archived_at` and appends a revision whose
  `changed_fields` is `["status"]`.
- No `UPDATE` or `DELETE` is ever issued against `goal_revisions`.

Storage notes: local file path from configuration; WAL off in this slice (single
process, short writes); `sqlite3` busy timeout configured; foreign keys enabled.
`changed_fields` and `prior_state` are JSON text columns.

`schema_version` holds one row per applied migration, so its primary key makes a
double-applied migration impossible rather than merely unlikely; the current version
is `MAX(version)`, and the migration runner writes the row inside the same transaction
as the migration body. A description/checksum ledger entry is deliberately deferred
while version 1 is the only migration.

## 6. Migration and compatibility

- Version 1 is the baseline. There is no existing data to migrate.
- Migrations are ordered `NNN_description.sql` files applied inside one transaction
  each, recorded in `schema_version`, with no down migrations.
- A database whose version exceeds the application's maximum fails startup with an
  `unavailable` diagnostic naming both versions; its data is not touched.
- Pre-1.0 compatibility policy: breaking HTTP changes require a recorded change note
  and a visible version bump. This is a recommendation pending the API-operations
  decision on compatibility and benchmark targets — not a binding commitment.

## 7. Trust and disclosure boundary

- Inputs are the owner's HTTP requests only. There is no source content in this slice,
  so no untrusted file or repository text reaches storage.
- Request bodies are never logged. Errors echo only the offending field name and the
  allowed values, never the submitted value.
- No credentials are stored or read. Configuration values are never returned by an API.
- Loopback binding is the only access control in this slice; local authentication and
  origin policy remain an open owner decision (`docs/requirements/security/grill-log.md`
  Q5). No external exposure is possible until that decision is made.

| Configure without editing source | startup | 7 | Invalid configured value |
